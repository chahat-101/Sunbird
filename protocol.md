# Sunbird — protocol, version 1

This is the wire format. Once links exist it is frozen: changing anything here
breaks every link already shared. Rationale is in `DECISIONS.md` and in
`docs/step-00-answers.md`, `-2.md` and `-3.md`. A later round supersedes an
earlier one where they differ: round 2 on record AAD, the record bound, the
slot entry layout and commit scope; round 3 on the header hash (the slot is
excluded), the slot bound, the final-record encoding and the decoder rules.
Step 01, before any link existed, amended two rules without changing a byte of
the format: `GET /api/meta/:id` returns raw leading bytes and the server keeps
no format knowledge (§3, §3.1, §6.4, §10), and unwrapping tries every known
entry before failing (§5). Step 02 made the fragment's four excess bits a
MUST (§2); every fragment a conforming encoder writes already satisfied it.
Step 03 wrote down a decoder rule the client already followed: a `0x01` entry
whose `length` is not 60 counts as a failed unwrap, not a malformed slot (§5).
Step 04 reworded a sentence in §5 that could be read as allowing several
legitimate `0x01` entries in one file; no rule changed. Step 05 wrote down the
metadata field rule the client already enforced (§7, §11), stating `size` over
a double so that implementations agree, and made a byte-order mark malformed.
Step 06 wrote down what every JSON parser in use already did with a duplicated
metadata key — the last occurrence wins (§7, §11) — and that an upload carries
`expires_at` and `max_downloads` as request parameters beside the blob (§10).
No byte of the format changed.
Before any link existed, the HKDF info strings (§4.3) were renamed from the
project's earlier name to `sunbird/v1/...`, and the §5 and §9 messages with
them. That changes every derived key, but no link had ever been shared, so no
file became unreadable; the version stays 1 and this is not a format change
made under an existing version.

The key words MUST, MUST NOT and MAY are used in the RFC 2119 sense.

All integers are big-endian. `‖` is byte concatenation. Offsets are in bytes.

---

## 1. Primitives

| Use | Primitive |
|---|---|
| Passphrase stretching | Argon2id, version 0x13 (RFC 9106) |
| Key derivation | HKDF-SHA256 (RFC 5869) |
| All encryption | AES-256-GCM, 12-byte IV, 16-byte tag |
| Header binding | SHA-256 |
| Randomness | CSPRNG (`crypto.getRandomValues`) |

AES-256, not AES-128: every HKDF output is 32 bytes, and there is no reason to
discard half of it.

---

## 2. URL

```
https://<host>/d/<id>#<fragment>
```

**`id`** — generated by the server after the upload completes. 96 random bits,
base64url, 16 characters. The server owns uniqueness; 96 bits makes
enumeration infeasible without any rate limit being load-bearing.

**`fragment`** — the 16-byte `fragment_secret`, base64url without padding.
It carries the secret and nothing else: no version, no flags.

A fragment MUST be exactly 22 characters from the base64url alphabet
(`A–Z a–z 0–9 - _`), with no padding, and the trailing four bits of the 22nd
character MUST be zero. A client MUST NOT emit, and MUST reject, any other
fragment. 22 characters hold 132 bits; only 128 carry the secret. If the four
excess bits were free, the fragment could carry something other than the
secret, and one secret would have sixteen spellings. Enforcing them is what
makes "the secret and nothing else" true — the same reason undefined `flags`
bits are rejected (§3.1). Of the 64 possible 22nd characters, exactly four
(`A Q g w`) are valid.

base64url rather than base58: links are pasted, not hand-copied, so avoiding
ambiguous glyphs buys nothing and costs a dependency.

**The URL never enters the cryptography.** Not the host, not the path, not the
ID — only the decoded fragment bytes. Send salts its KDF with the full share
URL, so opening a share through a different hostname derives a different key.
The ID is also assigned after encryption, so binding to it would be impossible
without a reserve-then-upload round trip.

## 3. Blob layout

```
blob = header ‖ record_0 ‖ record_1 ‖ … ‖ record_{n-1}
```

The header sits at the front of the blob, so a blob plus a fragment (plus the
passphrase, if set) is sufficient to decrypt even if the database is lost. The
server never interprets the header, nor any other byte of the blob: it has no
knowledge of the format beyond the byte caps in §3.1 and §6.4.

**Preview.** `GET /api/meta/:id` returns the first `min(8192, blob_size)`
bytes of the blob, and nothing else. The client parses the header out of them.
The server does not locate the end of the header; if the blob is shorter than
8 KiB the response also contains record bytes, which the client ignores.

### 3.1 Header

Fixed fields first, the one variable-length field last.

```
offset  size  field
0       1     version         0x01
1       1     flags
2       16    salt            random per file
18      8     expires_at      u64, absolute Unix time, seconds
26      4     max_downloads   u32
30      528   metadata_ct     512 bytes padded plaintext + 16 tag   (§7)
558     …     slot            entry_count ‖ entries                 (§5)
```

A v1 header with one slot entry is **622 bytes**
(30 + 528 + 1 + 1 + 2 + 60).

Three names for spans of the header:

```
header_prefix  bytes 0..29    version, flags, salt, limits   (30 bytes)
header_core    bytes 0..557   header_prefix ‖ metadata_ct    (558 bytes)
header         bytes 0..end   header_core ‖ slot             (variable)
```

`header_core` is fixed-length and never changes after upload. The slot may
grow (§5).

**Size bounds.** At most **64 slot entries**, and the whole header at most
**8 KiB (8,192 bytes)**. 64 entries of the largest defined type (`0x02`, 95
bytes each with type and length) give 558 + 1 + 64 × 95 = 6,639 bytes; the
byte cap also bounds entry types not yet defined, whose `length` could
otherwise reach 65,535. **These bounds are enforced by the client only.** The
server cannot find the end of the header without parsing the slot, and it
keeps no format knowledge (§3). A client MUST reject `entry_count > 64`, a
header over 8 KiB, or an entry whose `length` runs past the end of the bytes it
holds — at preview, the `min(8192, blob_size)` bytes from `GET /api/meta/:id`,
so a header over 8 KiB is always caught there.

**`version`** — `0x01`. See §9.

**`flags`** — bit 0 (least significant) = passphrase required. All other bits
MUST be zero; a client MUST reject a blob with any of them set. A new flag
therefore needs a version bump, which is deliberate: it stops a server probing
client behaviour with undefined bits.

The flag is unencrypted because the client needs it before it can derive
anything. **The server therefore learns which files have a passphrase.** Under
the D1 threat model this is accepted: a root admin already sees every row, and
the flag does not help them decrypt.

**`salt`** — 16 random bytes, fresh per file. Used as the Argon2id salt and as
the HKDF salt everywhere. Salts are public by design; storing it here is not a
leak.

**`expires_at`** — absolute time, not a duration. A duration would need an
upload timestamp, which the server controls, so the server could extend expiry
by lying about when the file arrived.

**`max_downloads`** — **`0` means no download limit**: the file expires by time
only. It does not mean "zero downloads allowed".

Both limits are fixed at encryption time. They cannot be extended after upload
without re-uploading (§8).

## 4. Key derivation

### 4.1 Passphrase (restricted mode only)

```
passphrase_bytes = UTF-8( NFC( passphrase ) )
pw_key           = Argon2id(passphrase_bytes, salt, v=0x13, m=65536 KiB, t=3, p=1, len=32)
```

- **NFC-normalize, do not trim.** Normalizing stops the same-looking passphrase
  failing between an iPhone and a Linux box. Trimming would silently discard a
  character the user typed.
- **Empty passphrase: rejected at upload.** Argon2id over an empty string is
  deterministic, so such a file would look protected while anyone with the
  link opens it. No composition rules beyond non-empty: Argon2id is the
  defence, and composition rules mostly produce worse passphrases. A length
  hint in the UI is fine; a validator is not.
- **v = 0x13** (Argon2 version 1.3, as RFC 9106 specifies). Stated explicitly,
  never left to a library default.
- **m = 64 MiB.** The only attacker who can grind this holds the link *and* the
  blob — not the D1 adversary, but a case worth making expensive. OWASP's
  19 MiB minimum was rejected as too cheap for that case; 64 MiB fits any
  phone from the last several years. Costs roughly 1–3 s on a mid-range phone,
  paid only when a passphrase is entered (approved).
- **t = 3.** RFC 9106's recommended pass count at this memory size.
- **p = 1.** `hash-wasm` is single-threaded in the browser. More lanes would
  change the output without changing the wall-clock cost, so p=1 states what
  actually happens.
- **len = 32.**
- **Fixed per version, never in the header.** Parameters in the header are
  parameters a malicious server can lower. Because they are fixed and the
  version is bound into every AEAD operation, weakening them needs a version
  bump, and an old client refuses an unknown version.

### 4.2 Keying material

```
ikm = fragment_secret ‖ pw_key       if flags bit 0 is set   (48 bytes)
ikm = fragment_secret                otherwise (public)      (16 bytes)
```

Public mode skips Argon2id entirely. Running it over an empty passphrase would
cost every public download 64 MiB and seconds of CPU for no security. This is
one function with one branch on the flag, not a second code path (D4).

A root admin holds `salt` and the blob but neither the passphrase nor the
fragment. To test a passphrase guess they would need the fragment too, so
there is nothing to test against (D2).

### 4.3 Derived keys

`HKDF(ikm, info, L)` below means HKDF-SHA256 with salt = header `salt`.

```
wrapping_key   = HKDF(ikm,      "sunbird/v1/wrap",           32)
file_key       = 32 random bytes, fresh per file
content_key    = HKDF(file_key, "sunbird/v1/content",        32)
nonce_base     = HKDF(file_key, "sunbird/v1/content-nonce",  12)
metadata_key   = HKDF(file_key, "sunbird/v1/metadata",       32)
metadata_iv    = HKDF(file_key, "sunbird/v1/metadata-nonce", 12)
```

Info strings are ASCII, no terminator. Every info string names the version, so
a version bump changes every derived key — a second defence behind the version
byte in AAD.

Everything except `wrapping_key` hangs off `file_key`, not off the
passphrase-derived key. That is what lets a future recipient who unwraps
`file_key` another way (§5, type `0x02`) read both content and metadata.

The HKDF salt is the header salt, **not** the file ID: the ID does not exist
until upload finishes, and binding crypto to a server-chosen identifier is the
class of mistake behind Send's host problem.

## 5. Key-wrapping slot (D3)

The content is encrypted under a random `file_key`, which is *wrapped* into
the slot rather than derived. v1 writes exactly one entry. The slot exists so
that v2 can add per-recipient entries next to it without a format change —
wrapping can emulate derivation, but not the reverse.

```
entry_count   u8
per entry:
  type        u8
  length      u16          length of body in bytes
  body        length bytes contents depend on type
```

A client MUST skip an entry whose type it does not know, using `length` alone,
without interpreting the body. That is the property that makes v2 additive.
A client MUST reject `entry_count = 0` or `entry_count > 64` (§3.1).

### Type `0x01` — fragment-derived (v1; body 60 bytes)

Used in both public and restricted mode; `flags` bit 0 decides whether `pw_key`
is part of `ikm`. The body is byte-identical in both modes, so a second type
would carry no information the flag does not.

```
iv            12   random
wrapped_key   32   AES-256-GCM(wrapping_key, iv, file_key, AAD)
tag           16
AAD           = version ‖ type           (2 bytes: 0x01 0x01)
```

AES-GCM rather than AES-KW: it is already in the stack, it is AEAD so the entry
type can be bound (a server cannot relabel an entry), and it avoids WebCrypto's
extractable-key handling for AES-KW.

### Type `0x02` — X25519 recipient (reserved; not implemented in v1; body 92)

```
ephemeral_pk  32
iv            12
wrapped_key   32
tag           16
```

A v1 client never writes this type and skips it when reading.

### Unwrapping

A client MUST try **every** entry of a known type, in slot order, continuing
past any entry that fails to unwrap. It uses the `file_key` from the first
entry that unwraps, and reports failure only when every entry is exhausted:

- if at least one `0x01` entry was tried and none unwrapped, report a wrong
  passphrase or damaged link;
- if no entry has a known type, report: *"This link needs a newer version of
  Sunbird."* — the file was not shared in a way this client can read.

**A `0x01` entry whose `length` is not 60** is treated as an entry that failed
to unwrap: the client continues to the next entry. It does not reject the
slot. This is not because such an entry might belong to someone else. Type
`0x01` is fragment-derived and its body is byte-identical in both modes, so
there is no legitimate `0x01` of another length, and no "someone else's"
`0x01` — per-recipient entries are type `0x02`. Rejecting would simply buy
nothing: a server that appends a junk entry to deny service could delete the
blob instead, and removing an entry is already conceded to be denial of
service (below). Continuing means a file with one good entry still opens. The
entry still frames by `length` like any other, so a bad `length` that runs
past the end of the header is still malformed (§3.1).

Stopping at the first failure is wrong. The slot is not covered by record AAD
(below), so an entry that fails says nothing about the entries after it: a
damaged or junk entry can sit in front of a good one. And the rule must hold
for types defined later. A v2 client that knows `0x02` may meet several `0x02`
entries, of which only one is its own. This is about future types, not `0x01`:
a file has exactly one legitimate `0x01` entry (above).

### The slot is not covered by record AAD

Records bind `header_core`, not the slot (§6.3). That is what lets v2 append
an entry to an **existing** file — share it with a new person — without
re-encrypting or re-uploading: `header_core` is unchanged, so every record
stays valid.

It is safe because each entry protects itself with its own AEAD:

- An attacker cannot forge an entry: they lack the wrapping key.
- Removing an entry is denial of service, which deleting the blob already
  achieves.
- An entry transplanted from another file does not unwrap under this file's
  wrapping key (the salt differs), and any `file_key` that does not belong to
  this file fails the metadata and every record.

A wrong `file_key` is self-detecting, so nothing in the slot needs the
records' protection.

## 6. Records

### 6.1 Sizes

```
rs                      = 65536   ciphertext bytes per record on the wire
tag                     = 16
delimiter               = 1
plaintext data / record = 65519   (65536 - 16 - 1)
```

64 KiB is the **ciphertext** record size, as RFC 8188's `rs`. The data capacity
is 65519. Getting these backwards is an off-by-one that only appears on files
near a record boundary.

### 6.2 Plaintext of a record and delimiters

```
record plaintext = data ‖ delimiter
delimiter        = 0x01   every record except the last
                   0x02   the last record, and only the last
```

No padding follows the delimiter: the delimiter is always the last plaintext
byte. D1 accepts that size leaks, and the server stores an exact byte count for
quotas anyway. The delimiter mechanism leaves room to add padding later (with a
version bump).

**End-of-stream is signalled by the `0x02` delimiter and by nothing else.**
It is not also in the nonce or in AAD — two sources of truth can disagree. The
delimiter is inside the plaintext, so GCM already authenticates it.

Every non-final record holds exactly 65519 data bytes. The final record holds
0 to 65519 data bytes. A file whose length is an exact multiple of 65519 ends
with a full `0x02` record. **An empty final record occurs only for a 0-byte
file**: exactly one record whose plaintext is the single byte `0x02`
(ciphertext 17 bytes). A decoder accepts a full final record; it is the
natural encoding.

### 6.3 Nonce and additional data

For record `i`, counting from 0:

```
nonce_i = nonce_base XOR I2OSP(i, 12)            (i zero-extended to 12 bytes)
AAD_i   = version ‖ SHA-256(header_core) ‖ I2OSP(i, 8)   (1 + 32 + 8 = 41 bytes)
record_i = AES-256-GCM(content_key, nonce_i, plaintext_i, AAD_i)   (ciphertext ‖ tag)
```

Nothing about the nonce is stored. A reordered record decrypts under the wrong
nonce and fails.

`SHA-256(header_core)` is in **every** record, not just the first. If only the
first record carried it, truncating to zero records would remove the binding.
The hash covers the version, flags, salt, both limits and the encrypted
metadata. It deliberately does **not** cover the slot (§5).

### 6.4 Size bound

```
max_plaintext = 100 MiB = 104,857,600 bytes
max_records   = floor(max_plaintext / 65519) + 1 = 1601
max_header    = 8,192 bytes
max_blob      = 8,192 + 1601 × 65536 = 104,931,328 bytes
```

The cap is on plaintext, because that is the number the user sees. 100 MiB is
not a multiple of 65519, so `floor(…) + 1` equals `ceil(…)` here. The server
cannot see plaintext length, so it enforces `max_blob` at upload, sized from
the 8 KiB header cap rather than a one-entry header. `max_blob` is a plain byte
count; it is the only format limit the server enforces. The header cap itself
is checked by the client (§3.1).

### 6.5 Decoding

Given the header (already parsed, §3) and `body = blob[header_len:]`:

1. If `len(body) = 0`, reject.
2. `n = ceil(len(body) / 65536)`. If `n > 1601`, reject before decrypting
   anything.
3. The last record is `len(body) − (n−1)·65536` bytes. If that is under 17,
   reject.
4. Decrypt records in order. Any authentication failure rejects the whole
   file.
5. Records `0..n−2` MUST end in `0x01`. Record `n−1` MUST end in `0x02`.
   Anything else rejects — in particular a last record ending in `0x01` is a
   truncated stream.
6. The total data length MUST equal the metadata `size`; a mismatch rejects
   the file. Both values are inside the AEAD, so an attacker cannot cause a
   mismatch — any mismatch is an implementation bug, caught at the moment a
   framing error would otherwise produce a silently truncated file.
7. Plaintext MUST NOT be released to the user until the final record has
   authenticated and step 6 has passed. (D5 assembles to a Blob, so this costs
   nothing.)

## 7. Encrypted metadata (D7)

```
json      = UTF-8( {"name": <string>, "type": <string>, "size": <integer>} )
plaintext = I2OSP(len(json), 2) ‖ json ‖ zero bytes to 512 total
metadata_ct = AES-256-GCM(metadata_key, metadata_iv, plaintext, header_prefix)
```

- `name` is the filename, `type` the MIME type, `size` the plaintext length in
  bytes.
- **Limit: 510 bytes of UTF-8 JSON after escaping.** The limit is in bytes: a
  Devanagari filename is three bytes per character, and JSON escaping expands
  further. The client checks the encoded length and rejects with a clear
  message; it never truncates.
- **Padded to 512** so the ciphertext length does not reveal how long the
  filename is. This is the one size leak that is cheap to close.
- **Length prefix, not terminator**: zero fill after a length prefix is
  unambiguous and needs no escaping rules.
- **The IV is derived, not random-and-stored.** `metadata_key` encrypts exactly
  one message per file, so a deterministic IV is safe. This replaces Send's
  all-zero metadata IV (`app/keychain.js:127`) at no storage cost.
- **AAD is `header_prefix`** (version, flags, salt, `expires_at`,
  `max_downloads`). So the header bytes served by `GET /api/meta/:id` give the
  client limits it can verify before downloading, not limits the server merely
  asserts. Verifying them requires unwrapping `file_key`, which in restricted
  mode requires the passphrase.

**Decoding.** After decrypting: `json_len > 510` → reject (malformed). Any
non-zero byte in the zero fill → reject (no legitimate encoder writes one, and
it would be a covert channel). The `json_len` bytes MUST be valid UTF-8 with no
byte-order mark, and MUST parse as a JSON object; otherwise reject (malformed).
The three defined keys MUST hold the defined kinds: `name` and `type` strings,
and `size` a number whose value, read as an IEEE 754 double, is an integer from
0 to 2^53−1 (so `3.0` is accepted and `-1`, `2.5` and `2^53` are not). A
missing defined key, or one holding anything else, → reject (malformed).

Unknown JSON keys → ignore. This is the one deliberately liberal rule, and it
covers only keys nobody defined: the JSON is inside the AEAD, so only the
uploader can add keys, never the server, and ignoring them is how a later
version adds a field without a version bump. A defined key with the wrong kind
of value is not unknown; it is malformed. Ignoring it would leave `size` for
§6.5 step 6 undefined, and two implementations would disagree about which files
open. Strict everywhere an attacker has reach.

**Duplicate JSON keys → the last occurrence wins.** A conforming encoder never
writes one. A decoder MUST use the last value of a repeated key, and the kind
rules above apply to that value: `{"size": "x", "size": 3}` is accepted with
size 3, and `{"size": 3, "size": "x"}` is malformed. Rejection is not required
because no implementation would perform it: `JSON.parse` and Python's `json`
both keep the last value and give no sign that a key repeated, and detecting it
takes a custom parser. A mandated rejection would be a rule silently broken
everywhere; last-one-wins is what the parsers already do, written down so that
they agree. It is safe for the same reason unknown keys are: the JSON is inside
the AEAD, so only the uploader can write it. A server cannot craft metadata at
all, and an uploader who repeats `name` could simply have written the second
value.

**Preview and download must agree.** Bytes 0..557 of the downloaded blob MUST
equal the previewed `header_core`, or the download is rejected. Without this,
verifying the limits at preview proves nothing about the download. The
comparison excludes the slot, which may legitimately have grown between preview
and download (§5); records start after the downloaded blob's slot.

**Decrypted metadata is hostile input.** Render it as text, never as markup,
and never trust `type` to choose how to display content (D7; six of
PrivateBin's twelve advisories came from this).

## 8. What the limits in AAD do and do not prove (D6)

Binding `expires_at` and `max_downloads` into AEAD proves what the **uploader
set**. It does not prove what the **server did**.

- A client can compare `expires_at` against its own clock.
- A client cannot know how many downloads already happened.

**Past `expires_at` by the client's clock, but served anyway: decrypt, and warn
prominently** — for example, *"The sender set this link to expire on 3 October.
The server provided it anyway."* Refusing would be theatre: the client already
holds the ciphertext and the key, and a drifted laptop clock would become "I
cannot open my own file". This is **the only server misbehaviour a client can
detect** — serving past the download count is invisible — so it must never
fail silently.

**The claim is only: a server cannot silently alter the limits an uploader
chose.** It can still serve past them. Say it in exactly those terms,
including in the README.

Consequence: limits are fixed at upload. There is no "keep this one more day";
the uploader re-uploads (approved). Mutable limits would need the server to
rewrite a value the client is supposed to verify.

## 9. Versioning

The version byte is the first byte of the header, and only there. It is bound
into every AEAD additional data (records, slot entries via `version ‖ type`,
metadata via `header_prefix`) and into every HKDF info string. A server that
rewrites it produces a decryption failure, not a weaker key.

**There is no negotiation.** The uploader's client picks the version, the
server stores the blob opaquely, and the downloader either understands it or
refuses. A client meeting an unknown version MUST refuse with:

> This link was created by a newer version of Sunbird. Update your client.

No fallback, no best-effort parse. A client that guesses at an unknown format
can be tricked into the weakest format ever shipped. A newer client MUST keep
decoding every older version.

**The version byte governs record framing and key derivation. It does not
govern the wrapping slot, which is extensible within a version.** Bump the
version byte only for a change to record framing, nonce derivation, HKDF
construction, or Argon2id parameters — and for a new `flags` bit (§3.1).
Adding a slot entry type is not a version bump, and neither is appending an
entry to an existing file (§5).

## 10. Procedures

### Upload

1. Generate `fragment_secret` (16), `salt` (16), `file_key` (32).
2. Choose `flags`, `expires_at`, `max_downloads`; build `header_prefix`. If
   the passphrase flag is set, reject an empty passphrase.
3. Derive `ikm` (Argon2id only if a passphrase is set), then every key in §4.3.
4. Build and encrypt metadata (§7) → `metadata_ct`.
5. Wrap `file_key` into one `0x01` entry → slot.
6. `header_core = header_prefix ‖ metadata_ct`; compute `SHA-256(header_core)`.
   `header = header_core ‖ slot`.
7. Encrypt records (§6); upload `header ‖ records` as the body of
   `POST /api/upload?expires_at=<decimal>&max_downloads=<decimal>`. The two
   parameters MUST be identical to the values in `header_prefix`.
8. Server returns `id`; client shows `https://<host>/d/<id>#<fragment>`.

The server cannot read the limits out of the blob, because it keeps no format
knowledge (§3); that is why they travel twice. The server's copy is
operational: it decides when the server stops serving and deletes the file.
The copy inside the AEAD is the one a downloader verifies (§8). They are two
representations of one decision, and a mismatch is a client bug.

The server refuses an upload whose `expires_at` is at or before its own clock,
or more than 7 days (604,800 seconds) after it. It never adjusts the value: the
header is sealed, and an adjusted row would disagree with it. A client MAY
choose a value a few minutes under 7 days, so that a device clock running fast
is not refused; the web client uses 300 seconds. That is a courtesy to the
user, not a limit — the server's bound is unchanged.

### Download

1. Decode fragment strictly (§2). Fetch the preview bytes (`GET /api/meta/:id`):
   the first `min(8192, blob_size)` bytes of the blob, unparsed by the server.
2. Parse the header out of them strictly: version known, reserved flag bits
   zero, slot well-formed and within the bounds of §3.1.
3. If flag bit 0, ask for the passphrase. Derive `ikm`, `wrapping_key`.
4. Unwrap `file_key`, trying every known entry before failing (§5). Derive the
   remaining keys.
5. Decrypt metadata; this verifies the limits. Show name and limits as text.
   If `now > expires_at`, show the expiry warning (§8).
6. Fetch the blob; check its `header_core` matches the preview; decode records
   and verify `size` (§6.5).

## 11. Decoder rules at a glance

Strict everywhere an attacker has reach; liberal only inside the AEAD, where
only the uploader writes.

| Input | Behaviour |
|---|---|
| Fragment not exactly 22 base64url chars; trailing 4 bits non-zero | Reject |
